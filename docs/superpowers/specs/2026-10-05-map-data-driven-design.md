# 西門町第二段：地圖改資料驅動 — 設計

> 承 `2026-10-05-ximending-map-design.md` 第五節「第二段」。本文件定案後，第二段的範圍與順序以本文件為準。

## 目標

把散在各系統裡的地圖數字收進一個資料檔，程式從它推算其餘的一切；第三段換新西門町時只換資料，不必再改各系統。

- 本段只換管線、不換內容：重構完成時，生成的世界和重構前完全一樣（重構前＝前置步驟把唐吉訶德招牌的亂數固定之後）
- 重構完成後，逐一修會沿用到第三段的既有 bug，每個 bug 一個 commit

**成功標準**

- 重構完成（下文第 10 步）時，快照和第 0 步記下的比對通過（比對方式見第二節，含 0.002 的數字容差）
- `world/constants.rs` 不再有道路常數（`X_*`、`Z_*`、`W_*`）與出生點常數（`PLAYER_SPAWN_*`）；程式碼裡找不到道路位置、路寬、地圖邊界、出生點的手抄副本（例如 `traffic_lights.rs`、`lifecycle.rs` 那種自抄的數字、`impl Default for MapBounds`）。散落的字面座標（霓虹招牌、任務等）屬第三段，不在此列。搜尋指令與結果附在收尾 commit 的說明裡
- 資料檔違反第一節列出的檢查時，遊戲啟動直接報錯並指出是哪一筆；CI 的讀檔測試在遊戲執行前就抓到。檢查擋不住的錯（例如路名打成另一條也會交會的路），第二段靠快照抓
- 每個 bug 修正的快照差異，只有該 bug 預期會動到的行

**範圍外**

- 新地圖需要的新能力全部移到第三段（第 1 批換新地圖時需要）：單行、斷面（兩側人行道、車道與分隔島位置）、中華路分隔島、多邊形徒步廣場、號誌三類、建築正面方向、小地圖重新設計。路段起訖不在此列：本段的資料格式本來就要記起訖
- 散落的字面座標（任務、行人路徑與 POI、霓虹招牌、可破壞物件、水坑等）：第三段第 4 批改用地名
- 建築擺放的問題（沿街建築錯軸、因重疊被略過的建築）：第三段第 1 批整批重蓋時處理，見第四節
- 第二段的資料檔是現在手做的西門町，不含 OSM 資料；第三段換成 OSM 衍生資料時，依第一段的授權段落把 OSM 衍生幾何和自創內容（店名、招牌）分檔

## 一、資料檔

**位置與載入**

- 資料檔 `assets/levels/ximending.ron`（依 `.agent/skills/asset-manager` 的慣例，`.ron` 放 `assets/levels/`），以 `include_str!` 編進執行檔（改地圖要重新編譯；換來的是不必處理執行期找不到檔案）
- 新模組 `src/world/map_data.rs`：型別（`serde` 反序列化）、讀檔、檢查、解析；在 `WorldPlugin::build` 讀入並插入成 resource。所有外掛的 `build()` 都在第一次 update 之前跑完，所以 Vehicle、Pedestrian、Ui 的 Startup 系統都拿得到；比 `WorldPlugin` 早加入的外掛不能在自己的 `build()` 裡讀它（目前沒有）
- 「載入資料檔並插入所有地圖 resource」做成一個函式，`WorldPlugin::build` 和需要真實地圖的測試（快照、行為測試）都呼叫它，不另外組一份；檢查錯誤的測試與推算規則的單元測試則自己組輸入
- RON 用 `bevy::asset::ron`（`bevy_asset` 的 re-export，0.10.1），不改 `Cargo.toml`；`serde` 已是直接依賴

**原則：資料只存「決定」，能推算的交給程式**

同一件事只能有一份。路寬寫在路網裡，斑馬線、號誌、路線、建築就不能再各自存一份「從那條路算出來的」座標，否則改一條路的寬度，其他幾份不會跟著變。

| 存在資料檔（決定） | 程式從路網推算 |
|---|---|
| 路網：每段路的路名、方向、位置、寬度、起訖、類型 | 路口位置、A* 網格的可走格、行人越界線與逃跑範圍 |
| 哪些路口有斑馬線、號誌（用兩條路名指定） | 斑馬線、號誌燈桿的實際位置 |
| NPC 車路線：依序經過的轉角（兩條路名，各帶一個車道係數） | 路線上每一個點（路口加減車道偏移） |
| 建築：路口建築（兩條路名＋哪個角）、沿街建築（路名＋哪一側＋在哪兩條橫路之間）、直接定位的建築（字面座標：統一元氣館原本寫成「中華路西緣再往西 10 m」，存成 50；第三段整批重蓋，不再追這個關係）；都含尺寸與名稱。建築是單一清單、每筆標明種類，順序＝現在的生成順序（路口 22 → 沿街 3 → 直接定位 13），見第三節 | 建築的實際座標 |
| 邊界、出生點 | `MapBounds`、邊界牆的位置（垂直於牆的座標＝邊界外 1 m；沿牆方向的中心＝地面平板中心，現在是 X −10、Z −15，不是邊界中點）、出生與重生位置 |

- **現在找不到規則的數字照原樣存**：例如 A* 網格範圍從 (−110, −90) 起 212 × 150 m（西邊比康定路外緣多 2 m、北邊比漢口街外緣多 4 m，套不出一條能剛好算出它的規則）、邊界牆的長度、厚度與高度、地面平板的中心與碰撞體大小、小地圖地標的偏移，以及小地圖的道路方塊（它自成一套：康定、西寧、中華長 180、中心 Z −15；漢中街長 100、中心 Z 0；東西向 5 條一律中心 X −10、長 200。和世界裡的路段不同——武昌、昆明、峨嵋在世界裡各分兩段，漢中街長 85）。硬推規則會讓快照改變；第三段換新地圖時再改成推算
- **人行道寬 4 m 統一成一份**：現在三個檔案共四處各自定義 4.0——`world/roads.rs` 兩處（`SIDEWALK_WIDTH` 常數與 `sidewalk_width` 區域變數）、`vehicle/spawning.rs`（車道偏移）、`pedestrian/behavior.rs`（公車站）；改成 `map_data.rs` 裡的一個常數（第二段不做成資料欄位，斷面欄位第三段才加）

**名稱**

- 路網的每一段屬於一條路（路名）；同一條路的各段方向與位置必須一致（例如峨嵋街分成漢中街以西、以東兩段）
- 路口用兩條路名指定（例如 `("中華路", "成都路")`）

**讀檔後一次解析**

讀檔後立刻把所有路名、路口、建築的角落換成座標；系統拿到的是解析後的結果，只負責生成。以下情況在啟動時報錯，訊息指出是哪一筆：

- 數值不合理：起點不小於終點、寬度不大於 0、路的位置（`at`）在邊界外。路的兩端可以伸出邊界：現在南北向道路從 Z −105 延伸到 75，邊界是 −94〜64
- 路名重複定義成不同方向或位置；用到不存在的路名
- 斑馬線、號誌、NPC 路線轉角指定的兩條路不是一南北、一東西，或沒有交會：兩條路的線交點，要落在雙方各自某一段的範圍內，或離段端不超過另一條路的半寬（容差 0.01 m）。要放寬到半寬，是因為現在的路都停在交會路的路緣附近：漢中街兩端在 Z ±42.5（北端是武昌街路緣，南端伸進成都路 0.5 m），武昌、昆明、峨嵋街在漢中街兩側各停在 X ±7.5
- 沿街建築的兩條橫路都要和它所沿的路交會，套同一條容差規則（現有 3 筆全部通過）
- 路口建築只檢查兩條路存在且一南北、一東西，不要求兩條路真的交會：現有 22 筆有 3 筆不交會——麥當勞、摩斯指定漢中街×漢口街（漢中街到不了漢口街），7-ELEVEN 指定康定路×峨嵋街（峨嵋街西段從 X −49 起）；第三段再收緊

推算規則（路口位置、車道偏移、建築座標、斑馬線與燈桿位置）集中在地圖模組，都是純函式：不開 App 就能寫單元測試，第三段的新地圖直接沿用。

**範例**

```ron
// 漢中街徒步區：武昌街到成都路
(street: "漢中街", axis: NS, at: 0.0, width: 15.0, from: -42.5, to: 42.5, kind: Pedestrian),
```

**第三段的新欄位**以 RON 預設值加入，已存在的資料不必改。

**資料怎麼產生**

- 數量多的（路網 12 段、建築擺放清單 38 筆：路口 22、沿街 3、直接定位 13）：先把函式裡的清單改成程式裡的型別清單（仍引用 `X_XINING` 這類常數名），再由測試輸出成 RON。路長這類算式由程式計算，不手算
- 數量少的（6 個斑馬線路口、4 個號誌路口、5 條車輛路線）：直接寫進資料檔
- 不論哪一種，寫錯都會被快照抓到

## 二、快照測試（第 0 步）

在改任何程式之前，把現在生成的整個西門町記成標準答案；之後每個重構 commit 都必須和它一樣。

**記錄生成完的結果，不記中間函式**：重構會拆函式、搬程式碼，只有最後生成的結果不能變；快照綁在函式上的話，一重構就壞。

**跑真正的啟動流程**：一個不開視窗的 App 測試（沿用 `world/buildings/facade.rs` 測試的 `MinimalPlugins + AssetPlugin` 寫法），照遊戲的順序跑：

- `setup_world`（地面與邊界牆、道路、建築、玩家與車、霓虹招牌、街道家具、斑馬線、特殊元素與掩體點）
- `setup_traffic_lights` → `spawn_world_traffic_lights`
- `spawn_initial_traffic`
- `setup_pathfinding_grid`（同時插入 `PointsOfInterest`）
- 小地圖與大地圖：`setup_minimap_hud`、`setup_full_map` 是 `ui` 底下私有模組 `setup_map` 的 `pub(super)` 函式，參數是 `&mut Commands` 與字型 handle；測試放在 `crate::ui` 底下，用一個一次性系統呼叫它們

不在測試裡另抄參數——抄了就測不到程式真正用的那一份。

**測試 App 的需求**（設計審查時用探針照本節流程實測過）：

- `init_asset` Mesh、StandardMaterial、Image（少了 Image，`roads_layout.rs` 的貼圖載入會 panic）；字型用 `Handle::<Font>::default()`，沒有 jpg／otf loader 也不會 panic
- 加 `TransformPlugin`；`MapBounds` 要自己插入（遊戲裡是 `WorldPlugin::build` 才 `init_resource`）
- rapier 碰撞體不需要 physics plugin 就建得出來；UI 不需要 `UiPlugin`；mesh 外框用 `bevy::camera::primitives::MeshAabb::compute_aabb()`（local 座標的中心與半長）
- Startup 順序照抄遊戲的 `.after(setup_world)`、`.after(setup_traffic_lights)`
- 規模：約 1,200 個實體、快照約 1.3k 行，跑一次 0.01–0.08 s

**記錄內容**

- 3D 實體每個一行：名稱、world 座標的位置、旋轉、縮放（測試 App 加 `TransformPlugin`，讀 `GlobalTransform`；只記 local 座標的話，同一種子物件在不同父實體底下會變成完全相同的行，例如 16 支號誌各 5 個一樣的子實體）、mesh 外框尺寸、碰撞體形狀與尺寸、和地圖有關的元件（建築名稱、號誌方向與 `is_primary`、NPC 車路線點與 `current_wp_index`）。mesh 外框一定要記：道路的長寬在 mesh 裡，不在 `Transform`
- 名稱：用 `Name`；沒有的話沿 `ChildOf` 往上找最近一個有 `Building` 的祖先（含自己），用它的 `Building.name`（建築名稱放在 `Building` 元件，不在 `Name`）；兩者都沒有就記空字串（道路、斑馬線、牆、號誌與車輛的子實體大多如此，靠位置與尺寸區分）
- 不記：`VehicleId`（全域計數器，`cargo test` 同一個行程裡會受其他測試影響）、亂數產生的元件值（`NeonSign.phase_offset`）
- 資源：`MapBounds`、A* 網格可走格（逐列壓縮）、`PointsOfInterest`
- 小地圖與大地圖：每個 UI 節點的 `Node` left／top／width／height（測試沒有 `UiPlugin`，不跑 layout）、`Text` 內容（大地圖的路名；改讀資料檔後路名打錯字也看得出來——repo 裡「峨嵋」「峨眉」兩種寫法都有），加上兄弟索引路徑（例如 `minimap/0/0/12`）：bevy_ui 依兄弟順序疊放，後生成的蓋在上面，排序不能抹掉這個順序
- 全部實體都記、不篩選：快照只用一陣子，自己篩「哪些和地圖有關」反而可能漏掉跟著地圖算的子物件

**格式**

- 純文字、每行一個實體、整份排序：3D 實體的生成順序改變不算差異（UI 的疊放順序由兄弟索引路徑保留）
- 數字四捨五入到 0.001、−0 當 0
- 旋轉不記四元數，改記旋轉後的 X 軸與 Z 軸方向（`rot * Vec3::X`、`rot * Vec3::Z`）：同一個旋轉有 q 和 −q 兩種四元數，繞 Y 轉 180° 時 w ≈ 0，`from_rotation_y(PI)` 和 `from_rotation_y(-PI)` 的 y 一個是 +1、一個是 −1，正規化成 w ≥ 0 也救不了（現在有 4 支號誌與自動販賣機是這種角度）；旋轉後的軸只有一種寫法
- 比對分兩段：先以 multiset（計數）逐行比對，重複的行少一行也看得出來；剩下對不上的行，結構相同且每個數字差 ≤ 0.002 的視為相同——四捨五入邊界附近的值（探針實測有 15 個離邊界不到 0.00002），以及 CI（Ubuntu）和 macOS 的 sin／cos 可能差 1 ulp，都靠這一段吸收；比對通過時也輸出被吸收的行數
- 檔案 `src/world/snapshots/ximending_world.txt`，提交進 repo
- 不一致時列出「少了哪幾行、多了哪幾行」；刻意更新時跑 `UPDATE_SNAPSHOTS=1 cargo test map_snapshot`，修 bug 的 commit 用 git diff 就看得到哪些東西移動了
- 不用 insta：它多出來的互動式審核在這裡用不到，排序過的文字檔用 git diff 就夠清楚，也不必新增依賴

**先證明快照穩定、而且抓得到改變**

- 同一份程式連跑兩次，快照完全相同（前置步驟把隨機招牌改成可重現之後）
- 每一類（道路、建築、斑馬線、紅綠燈的本地常數、NPC 路線、A* 網格、小地圖、`MapBounds`、邊界牆，以及上表每一項）各故意改一個數字，確認測試失敗、失敗的是預期那幾行；改完手動改回
- 產生快照後抽幾行對照常數（例如漢中街 mesh 長 85；中華路是寬 32 的車道 mesh 加兩條寬 4 的人行道 mesh，中心偏移 ±18），確認記到的是對的東西

**重構前的截圖**：第 0 步同時用 `cargo brp` 拍一組基準截圖（預設鏡頭 08:00、21:00、開小地圖、開大地圖），供第 10 步比對。行人與 NPC 車會動，畫面不會逐像素相同；嚴格的比對靠快照，截圖用來目視確認道路、建築、招牌、小地圖沒變。

**現有的 bug 也原樣記進快照**（例如阿宗麵線的位置）：快照記的是現在的樣子，修 bug 的 commit 才讓它改變。

**快照的壽命**：只服務第二段。第三段第 1 批換新地圖時刪除，改用規則型測試（見第四節的三項檢查）。

## 四、修 bug

重構全部完成後才修：第 10 步需要一個「整段重構後畫面沒變」的乾淨檢查點，穿插修 bug 就做不了這個整體比對。

**範圍：只修會沿用到第三段的規則。** 建築擺放在第三段第 1 批會依新規劃整批重蓋，第二段不動。

**每個 bug 一個 commit**

1. 先寫會失敗的測試，證明 bug 存在
2. 只改程式（推算規則或系統），資料檔不動
3. 快照有變時用 `UPDATE_SNAPSHOTS=1` 重新產生，逐行檢查差異：只能有預期的變化，有任何意料外的一行就停下來查
4. 開遊戲截圖確認；CHANGELOG 加在 Fixed

**Bug 1：小地圖南北顛倒**

- 投影用 `-z × 比例`，但世界的 +Z 是南（漢口街 Z −80 在北、成都路 Z 50 在南），南方被畫在上面（上下鏡像；東西方向是對的）。第 0 步截圖：紅樓（成都路以南）畫在小地圖最上方、標 N 的那一側
- 第 4 步已把投影合成一份，這裡只改一處，小地圖、大地圖的道路與地標、玩家標記的位置、GPS 標記一起修正
- 紅燈測試：漢口街在小地圖上方、成都路在下方；目的地在北邊時 GPS 標記在玩家上方
- 第二節行為測試表裡小地圖、大地圖、GPS 三列的字面期望值，在這個 commit 一起改成修正後的值

**Bug 2：小地圖、大地圖的玩家箭頭不會轉**

- `update_minimap`、`update_fullmap` 把旋轉寫進 3D 的 `Transform.rotation`，但 Bevy 0.17 的 UI 只讀 `UiTransform`（`Node` 必帶的元件，旋轉欄位是順時針的 `Rot2`），bevy_ui 不讀 3D `Transform`——依原始碼判斷，箭頭永遠朝上。第 0 步實機確認：按住 W+D 讓玩家轉向（鏡頭從朝北的漢口街一側轉到朝西南的成都路、康定路一側）後，小地圖箭頭仍朝上（只按 D 是平移，角色不會轉向）
- 角度式也要重推：現在的式子以 +Z 為上，Bug 1 修好後北（−Z）才是上
- 這個 bug 和投影無關，不會因為 Bug 1 修好而消失，所以另外一個 commit
- 紅燈測試斷言 `UiTransform`（不是 `Transform`，否則畫面沒變測試也會過）：面向東時箭頭朝右（修好前箭頭永遠朝上，所以「面向北時朝上」修好前也會過，只能當輔助）；旋轉有插值，係數是 `min(10·dt, 1)`，要跑兩次 update、第二次 dt ≥ 0.1 s

**疑似 bug：行人越界線在最外圍道路的中線**

- 越界線 X −100〜80、Z −80〜50 是四條外圍道路的中線，不是地圖邊界（X −119〜109、Z −94〜64）：走在康定路西側、中華路東側、漢口街北側、成都路南側那半邊的行人會被立刻移除
- 第 0 步的行為測試記下現在的行為；確認是 bug 就列為第 3 個 bug commit，越界線改成地圖邊界（這條推算規則第三段會沿用）；不是就照原樣保留

**Bug 4：斑馬線條紋轉了 90°**（重構第 5 步的審查從快照找到，納入第二段）

- `roads.rs` 的 `spawn_zebra_crossing` 把「沿 X 延伸的斑馬線」的條紋排成 X 5 m × Z 0.5 m、沿 Z 排開：橫跨 15 m 的漢中街，實際只蓋住中間 5 m，還往路口裡伸 4 m 多。所有路口都是
- 改成條紋 X 0.5 m × Z 5 m、沿 X 排開橫跨整條路（沿 Z 延伸的斑馬線同理）；這條繪製規則第三段沿用
- 紅燈測試：抽出純函式算條紋的位置與尺寸，沿 X 延伸的斑馬線第一條在 X 最左側、尺寸 0.5 × 5

**Bug 5：T 字路口在沒有路的那一邊也畫斑馬線**（同上）

- 斑馬線一律畫路口四邊，6 個路口有 4 個是 T 字：漢中街×武昌街沒有北邊、漢中街×成都路沒有南邊、西寧南路×峨嵋街與西寧南路×武昌街沒有西邊，卻都畫了
- 路口解析時順便算出哪幾邊真的有路（該方向有路段伸出交會路的路緣），斑馬線只畫在有路的那幾邊；第三段的號誌三類也會用到
- 紅燈測試：漢中街×武昌街只有南、西、東三邊；快照差異只有那 4 條斑馬線消失

## 風險

- **容差比對可能蓋掉真正的小變化**：每個數字差 ≤ 0.002（不論單位是公尺、px 或方向分量）都視為相同。位置與尺寸真的改錯，通常是公尺等級（例如用錯路寬、用錯軸），不會小到這個程度；比對通過時輸出的「被容差吸收」行數突然變多，就要查原因
- **快照只看得到 Startup 的結果**：執行中才用到的數字靠第二節的行為測試；那張表漏一項，重構就可能悄悄改到它，所以寫測試前的完整盤點不能省
